The RAG pipeline in this repo, component by component

Control-theory PDFs go in one end. A physics-based reward expression for CartPole comes out the other. This walks every stage, with the exact input and output shape of each, assuming no prior knowledge of retrieval systems.

Haystack 2.x Qdrant · dense BM25 · sparse all-MiniLM-L6-v2 ms-marco-MiniLM-L-6-v2 gpt-4.1

What RAG is, in one page

A language model knows only what was in its training data. If you want it to answer using your documents — these specific control-theory papers — you have two options: retrain the model (expensive, impractical), or find the relevant passages yourself and paste them into the prompt. The second one is Retrieval-Augmented Generation. That is the entire idea.

So a RAG system is really two systems glued together:

  1. A search engine over your documents (the retrieval half). Built once, offline: you chop documents into passages and index them so they can be looked up fast. Then at query time you ask it for the top handful of passages.
  2. A prompt-builder plus LLM call (the generation half). You take those passages, drop them into a prompt template with your actual question, and send it off.

In this repo the "question" is unusual — it isn't a question a human reads an answer to. It's "given these paper excerpts about pendulum energy and Lyapunov functions, write me a reward-function formula." The LLM's output is a one-line math expression that later becomes the reward signal for a reinforcement-learning agent. The retrieval half is completely standard RAG; only the payload is exotic.

Two more terms you need before the map, because every component below is one or the other:

  • Dense retrieval — each passage is turned into a list of numbers (a vector) that encodes its meaning. Search = find the passages whose vectors point in a similar direction to the query's vector. Catches meaning: a query about "energy of inverted pendulum" can match a passage that says "kinetic plus potential term of the pole" with no shared words.
  • Sparse retrieval (BM25) — classic keyword matching with smart weighting for rare words. Catches exact tokens: Lyapunov, theta_dot, a specific equation number. Blind to synonyms.

Each misses what the other catches, so this pipeline runs both and merges the results. That's what "hybrid retrieval" means, and it's the central design decision of the code.

Phase one — ingestion, run once

Everything in this phase happens before you ever ask a question. The product of the phase is two indexes on disk that the query side attaches to.

01Corpus

Source documents

rag/rag_source/ · rag/rag_parsed/ · rag/rag_seed/

The knowledge base: control-theory and RL papers as PDFs, plus hand-written Markdown notes. Nothing clever here, but one thing matters — the pipeline can only ever answer from what is in this folder. If no paper discusses pendulum energy shaping, no amount of retrieval tuning will produce a good reward expression.

InputYou, dropping files in a folder.
OutputPDF files, and/or .md files.
Consumed byMarker (PDFs) or the Markdown loader directly.
02Parsing

Marker — PDF to structured JSON

external tool (github.com/datalab-to/marker), output under rag/rag_parsed/marker/<paper>/

A PDF is a drawing format, not a text format: it stores glyph positions, not sentences. Naive extraction on a two-column paper gives you interleaved garbage and destroys every equation. Marker is a document-AI tool that recovers the actual structure — reading order, headings, paragraphs, captions, equations — and exports it as JSON.

Marker runs outside this pipeline; the repo only reads its output. Per paper it produces a directory the code treats as a triplet:

  • blocks.json — the one that matters. A nested tree of layout blocks, each with a block_type (Text, Equation, Caption, …), an html string, and children.
  • <paper>.json — linearized content, used only as a fallback.
  • <paper>_meta.json — optional metadata, carried along for provenance.

discover_marker_triplets() finds these by walking for every blocks.json under the root, treating the folder name as the source tag (murray_lyapunov → murray_lyapunov.pdf).

InputOne PDF.
OutputA folder: blocks.json (block tree with HTML), content JSON, meta JSON.
WhyPreserves equations, section structure, and reading order that plain text extraction loses.
03Chunking

Loaders — JSON/Markdown to Haystack Documents

haystack_ingestion_md.py · load_marker_as_documents() · load_md_as_documents()

A retrieval system does not index whole papers; it indexes chunks. The reason is mechanical: you will later paste retrieved text into a prompt with a size limit, and a hit that says "somewhere in these 30 pages" is useless. Chunks should be small enough to be precise, big enough to stand alone.

This repo picks chunk boundaries that already exist in the document instead of cutting every N characters:

  • Marker path — collect_blocks() walks the block tree recursively and emits one Document per block that has non-empty HTML. A paragraph becomes a chunk; an equation becomes its own chunk; a figure caption becomes its own chunk. Two fallbacks exist if the blocks carry no HTML: flatten every html field found anywhere in the content JSON, and failing that, dump the raw content JSON as a single Document.
  • Markdown path — _split_markdown_sections() regex-matches headings # through ###### and makes each section's body a Document, recording section and level in metadata. Text before the first heading becomes a preface chunk.

The unit everything downstream speaks in is the Haystack Document — a small object with three fields you care about: id, content (the text), and meta (a free-form dict). After this step, a 40-page paper is a few hundred Documents and the pipeline no longer cares where they came from.

InputPath to blocks.json (+ content/meta), or to a .md file.
OutputList[Document]; content = HTML block or MD section body, meta = {source, block_type|section, level, format}.
ScaleOne paper → hundreds of Documents. The repo's bm25_cache.jsonl is ~12 MB of them.
Worth knowing

The content stays as raw HTML (<p>…</p>, <math> fragments) — tags are never stripped. So the embedder and the LLM both see markup along with the prose. It works, but those tags cost tokens and dilute the embedding slightly.

04Identity

Stable IDs — making re-ingestion safe

haystack_ingestion_md.py · _stable_id() · assign_ids()

Every Document gets id = sha1(source + "\0" + content) — a fingerprint of its text. Identical text from the same source always produces the identical ID.

That single trick buys idempotency: re-running ingestion on a folder you've already ingested writes the same IDs, and both stores are told DuplicatePolicy.SKIP, so nothing is duplicated and nothing is re-embedded needlessly. Add one new paper to the folder, re-run, and only that paper's chunks are new. Without this you would get the whole corpus twice, and every retrieval result would come back in pairs.

InputList[Document] with no IDs.
OutputSame list, each .id set to a 40-char hex digest.
Side effectEdit one word in a chunk and its ID changes — the old copy stays in the index as an orphan until you --recreate-index.
05Dense path

The embedding model

SentenceTransformersDocumentEmbedder · sentence-transformers/all-MiniLM-L6-v2

An embedding is a fixed-length list of numbers that represents a piece of text's meaning. This model maps any text to 384 numbers. The useful property: texts with similar meaning land near each other in that 384-dimensional space, so "closeness of vectors" becomes a usable proxy for "similarity of meaning". That's the whole basis of semantic search.

Two details that trip people up:

  • The model has an input limit (a few hundred words). Text past it is silently truncated — another reason chunks are block-sized.
  • The same model must embed documents and queries. Two different models produce incomparable coordinate systems. Hence all-MiniLM-L6-v2 appears in both the ingestion and the query script.

index_documents() embeds in batches of 128 (--batch-size) so memory stays flat on a 100-page document. It runs on CPU; it is the slow part of ingestion.

InputList[Document] (the content strings).
OutputSame Documents with .embedding = list[float] of length 384.
Coupled to--embedding-dim 384 on the Qdrant collection. Mismatch = hard failure.
06Dense path

Qdrant — the vector database

QdrantDocumentStore · build_stores() · ./rag/qdrant_papers on disk

A vector database stores embeddings and answers one question very fast: given this query vector, which stored vectors are nearest? Scanning every vector would be linear in corpus size, so Qdrant builds an approximate-nearest-neighbour index instead.

Configuration used here:

  • index — collection name, default "papers". This is a namespace inside the database.
  • path=./rag/qdrant_papers, on_disk=True — embedded mode. No server to run; the DB is a folder in the repo. Drop the path and you get :memory:, which vanishes when the process exits.
  • recreate_index — False by default in the ingestion scripts, so data survives re-runs. --recreate-index wipes the collection.
  • embedding_dim=384 — fixed at creation time.
Input (write)Documents carrying 384-float embeddings, policy SKIP.
Input (read)A 384-float query vector + top_k.
Output (read)List[Document] with .score = vector similarity, sorted best-first.
Persistence./rag/qdrant_papers/ — survives restarts; this is why ingestion is a one-time cost.
07Sparse path

BM25 store and the JSONL cache

InMemoryDocumentStore · bm25_cache.jsonl · save_documents_jsonl()

The keyword half needs the raw text, not vectors. Haystack's InMemoryDocumentStore holds the Documents in RAM and computes BM25 scores on demand.

"In memory" creates a problem: it's empty every time a process starts. The fix in this repo is bm25_cache.jsonl — one JSON object per line, {id, content, meta}, written at the end of ingestion by save_documents_jsonl(). Any later process calls build_sparse_store(), which reads that file, de-duplicates by ID, and repopulates the store in seconds. So the cache is the sparse index's on-disk form, the exact counterpart of the rag/qdrant_papers/ folder.

How BM25 itself scores, briefly: a passage scores high when it contains the query's words, more if those words are rare across the corpus (so Lyapunov counts far more than the), with diminishing returns for repetition and a penalty for passage length. No neural network, no training, no GPU — and unbeatable when the query contains an exact term.

Input (write)Documents with text, policy SKIP; mirrored to bm25_cache.jsonl.
Input (read)The raw query string + top_k — no embedding involved.
Output (read)List[Document] with .score = BM25 score, sorted best-first.
Failure modeCache missing → store silently empty → sparse branch returns nothing and you've degraded to dense-only. The script logs a warning.

Phase two — retrieval, per query

All of this lives in haystack_query_pip.py, in the class HybridQueryEngine. Its query() method is the whole phase in five lines: dense retrieve, sparse retrieve, fuse, rerank, return. Defaults come from the QuerySettings dataclass.

08Dense path

Query embedder

SentenceTransformersTextEmbedder · HybridQueryEngine.dense_retrieve()

Same model as step 5, different entry point: it takes one string rather than a list of Documents. The query becomes a point in the same 384-dimensional space the corpus lives in, which is the only way "nearest" means anything.

Inputtext: str — e.g. "cartpole energy function: upright pole, ..."
Output{"embedding": list[float]}, length 384.
CostOne small forward pass; warm_up() loads the model once at engine construction.
09Dense path

Dense retriever

QdrantEmbeddingRetriever · dense_k = 20 (24 in the CartPole script)

Hands the query vector to Qdrant and gets back the dense_k nearest chunks. These are the semantic candidates: passages about the same concept even when they share no vocabulary with the query.

Inputquery_embedding: list[float], top_k: int.
OutputList[Document], length ≤ dense_k, ranked by vector similarity.
Tune by--dense-k. Larger = better recall, more work for the reranker.
10Sparse path

Sparse retriever

InMemoryBM25Retriever · sparse_k = 40 (60 in the CartPole script)

Runs in parallel with the dense branch and never touches an embedding — the raw query string goes straight in. Note the default asymmetry: sparse_k is double dense_k. BM25 is cheap and noisier, so the code casts a wider net on that side and lets fusion and reranking sort it out.

Inputquery: str, top_k: int.
OutputList[Document], length ≤ sparse_k, ranked by BM25 score.
Tune by--sparse-k.
11Merge

Reciprocal Rank Fusion

haystack_query_pip.py · rrf_fuse(dense, sparse, k=60, weight_dense=1.0, weight_sparse=1.0)

Now you hold two ranked lists whose scores are incomparable — cosine similarity around 0.7 versus a BM25 score of 14.2. Normalizing them is guesswork. RRF sidesteps it by throwing the scores away and using only the ranks:

fused_score(doc) = Σ over lists  weight_list × 1 / (k + rank_in_list)
                   with k = 60, ranks 1-based

Each list's first result contributes 1/61 ≈ 0.0164, its second 1/62 ≈ 0.0161, and so on. Two consequences, both intentional:

  • A document that appears in both lists accumulates two contributions and jumps to the top. Agreement between two very different retrievers is strong evidence of relevance.
  • The k = 60 offset flattens the curve, so rank 1 isn't overwhelmingly better than rank 5 — it limits the damage when one retriever is confidently wrong.

Implementation detail: scores accumulate into a dict keyed by document ID, so the union de-duplicates automatically; the fused score is written back onto doc.score, overwriting the retriever's original score. --wd and --ws let you trust one branch more than the other; both default to 1.0.

InputTwo List[Document] (dense, sparse), each ranked.
OutputOne de-duplicated List[Document] sorted by fused score — up to dense_k + sparse_k items (≤ 60 by default).
Notedoc.score now holds the RRF value (~0.01–0.03), not a similarity. Don't read it as a confidence.
12Precision

Cross-encoder reranker

cross-encoder/ms-marco-MiniLM-L-6-v2 · HybridQueryEngine.rerank() · final_k = 10 (12 in the CartPole script)

Retrieval so far has been fast-but-approximate by construction. The embedding model encoded each chunk without ever seeing your query (that's a bi-encoder, and it's the only way to precompute an index). A cross-encoder does the opposite: it reads the query and one passage together and scores how well that passage answers that query. Far more accurate, and far too slow to run over a whole corpus — but perfectly affordable over the ~60 survivors of fusion.

So the shape of the pipeline is a funnel: cheap recall first, expensive precision last.

corpus (10⁴–10⁵ chunks)
  → dense 20  +  sparse 40      cheap, parallel
  → RRF union ≈ 60              free
  → cross-encoder → top 10      expensive, accurate

The code has two paths because API names differ across versions: the Haystack component (reranker.run(query=…, documents=…)), and a fallback to sentence_transformers.CrossEncoder.predict() over (query, content) pairs. Both end with .score replaced by the cross-encoder score and the list truncated to final_k. Pass --no-rerank and this becomes a plain docs[:final_k] slice of the RRF order.

Inputquery: str + the fused List[Document].
OutputList[Document] of length final_k, .score = cross-encoder relevance.
This is the endof retrieval. Everything after consumes these passages as plain text.

Phase three — generation

The "AG" of RAG. In cartpole_rag_llm_ppo.py, haystack_seed_reward() builds the engine and calls engine.query(), then hands the texts to llm_generate_seed_expression().

13Generation

Prompt assembly

cartpole_rag_llm_ppo.py · llm_generate_seed_expression()

The retrieved Documents are reduced to their content strings, and only the top 5 are used — "\n\n".join(texts[:5]) — even though final_k = 12 were retrieved. The remaining 7 are dropped at this line. That slice is the single tightest bottleneck in the system: it is what the model actually reads.

The context is interpolated into a template that is deliberately prescriptive, because the output has to be machine-evaluable, not prose. It specifies:

  • The goal — a positive, physics/energy-based reward that rewards an upright pole, a centred cart, and low velocities.
  • The exact variable names allowed — x_n, x_dot_n, theta_n, theta_dot_n, u_n (all normalized), with an explicit ban on inventing symbols like w1, w2.
  • The syntax — Python, ** for powers, allowed functions abs() sin() cos() tanh() plus wrap() for angles.
  • The format — "Return ONLY the mathematical expression, nothing else."

A system message sets the role ("expert in control theory and reinforcement learning"). This is the part people mean by "prompt engineering": every constraint exists because the downstream code will eval() the string, and anything unexpected crashes it.

InputList[str] of retrieved passage texts.
OutputTwo chat messages: system role + user prompt with the 5 passages inlined.
GroundingThis is where retrieval pays off — the formula is written against passages from your papers, not the model's memory.
14Generation

The LLM call

openai.OpenAI().chat.completions.create · model gpt-4.1 · temperature 0.6 · max_tokens 200

One API call. temperature 0.6 leaves real randomness, so two runs give two different reward functions — relevant if you are comparing training curves and expect reproducibility. max_tokens 200 is a hard cap that fits a one-line formula with room to spare. The key comes from OPENAI_API_KEY (there's a .env in the repo; it must not be committed).

The raw reply is written to runs_cartpole_llm_ppo/seed_expr_<save_index>.txt before any processing — your audit trail of what the model actually said. Errors are re-raised, so a missing key or a refusal stops the run rather than silently falling back (the fallback expression is commented out in the source).

InputThe two chat messages from step 13.
OutputA single string, e.g. 1 - (theta_n**2 + 0.1*theta_dot_n**2 + 0.1*x_n**2).
Artifactruns_cartpole_llm_ppo/seed_expr_7.txt
Not verified

Nothing checks that the expression reflects the retrieved passages, or that it is physically sensible — only that it parses when evaluated later. In RAG terms there is no faithfulness or citation check; the papers constrain the model's input, not its output.

15Generation

Variable normalization

cartpole_rag_llm_ppo.py · _normalize_vars() · _VAR_ALIASES

LLMs paraphrase variable names even when told not to — theta for theta_n, omega for theta_dot_n, force for u_n. _normalize_vars() rewrites them with word-boundary regexes, longest alias first so theta_dot is handled before theta. A small, unglamorous component that is the difference between an expression that evaluates and a NameError.

InputRaw expression string from the LLM.
OutputSame expression using only x_n, x_dot_n, theta_n, theta_dot_n, u_n.
Returned asseed_expr — the final product of the RAG pipeline.
16Downstream

Where the output goes

cartpole_rag_llm_ppo.py · _canon_ops_from_expr() → sample_sr_dataset() → fit_symbolic_reward() → SymbolicRewardCartPole

RAG hands over a string; here is what consumes it, kept brief by design.

_canon_ops_from_expr() scans the expression for which operators it used and turns that into the operator sets (abs/sin/cos/tanh, + - * /) allowed in the search that follows — so retrieval influences not just the formula but the shape of formulas considered next. sample_sr_dataset() then draws 6,000 random normalized CartPole states, evaluates the seed expression on each, and produces an (X, y) table. fit_symbolic_reward() runs PySR symbolic regression on that table to find a compact formula that reproduces the same values (falling back to Ridge regression on quadratic features if PySR or Julia is unavailable). The result is wrapped by SymbolicRewardCartPole, which computes 1.0 + 0.5 × expr per step as the environment's reward, and a PPO agent trains against it and against stock CartPole for comparison. Training mechanics are out of scope here.

Inputseed_expr + inferred operator sets.
Outputruns_cartpole_llm_ppo/: symbolic_expression_ppo_*.txt, learning-curve CSVs, learning_curves_ppo_*.png, summary CSV.
BoundaryRAG ends at step 15. Everything in this card is the consumer.

Running it

Ingest once, then query as often as you like.

# 1. install
pip install haystack-ai qdrant-client qdrant-haystack sentence-transformers torch accelerate

# 2. ingest — builds ./rag/qdrant_papers + ./rag/bm25_cache.jsonl
python rag/haystack_ingestion_md.py \
  --marker-root rag/rag_parsed/marker \
  --md-root rag/rag_seed/md \
  --qdrant-collection papers \
  --qdrant-persist ./rag/qdrant_papers \
  --embedding-model sentence-transformers/all-MiniLM-L6-v2 \
  --embedding-dim 384 \
  --batch-size 128 \
  --bm25-cache ./rag/bm25_cache.jsonl

# 3. inspect retrieval on its own — always do this before blaming the LLM
python rag/haystack_query_pip.py \
  --qdrant-collection papers --qdrant-persist ./rag/qdrant_papers \
  --bm25-cache ./rag/bm25_cache.jsonl \
  --dense-k 20 --sparse-k 40 --final-k 10 \
  --query "what is lyapunov stability?"

# interactive variant
python rag/haystack_query_pip.py --interactive

# 4. retrieval → LLM → symbolic regression → PPO
export OPENAI_API_KEY=...
python rag/cartpole_rag_llm_ppo.py

Step 3 prints one line per hit — #rank [score | source | block_type] first 160 chars. If the passages there are off-topic, the generated reward will be too; fix retrieval first.

Traps in this code

Observations from reading the files, not criticism of the approach — these are the things that will cost you an afternoon.

  • Three ingestion/pipeline files, two designs. haystack_ingestion_md.py (Marker + Markdown) is the current one per the README; haystack_ingestion.py is the same thing minus Markdown. haystack_pipeline.py is an older self-contained prototype that fuses differently (min-max normalize + union, keep best score) and reranks with BAAI/bge-reranker-base. It also sets recreate_index=True and DuplicatePolicy.OVERWRITE — running it will wipe your collection. The live path is ingestion_md → query_pip.
  • Collection name vs folder name. The README's example passes --qdrant-collection qdrant_papers, while both scripts default the collection to papers and the folder to ./rag/qdrant_papers. Ingest into one collection and query another and you get zero hits with no error — the collection name must match on both sides.
  • Silent half-failure. Missing bm25_cache.jsonl logs a warning and leaves the sparse store empty; you still get results, just dense-only. Check the "Loaded N docs into BM25" line.
  • Score meaning changes per stage. doc.score is a vector similarity, then a BM25 score, then an RRF value, then a cross-encoder logit. Never compare across stages.
  • Edited chunks leave orphans. IDs hash the content, so an edited passage is written as a new document while the stale copy remains until --recreate-index.
  • Retrieval is not reflected in the embedding of markup. HTML tags are indexed verbatim; stripping them before embedding would likely improve both retrieval and prompt density.
  • The --streaming flag is inert in haystack_ingestion_md.py — it logs that it's falling back to batch. The real streaming path exists only in haystack_ingestion.py.
  • eval() on model output. The generated expression is evaluated with {"__builtins__": {}} and a small allowlist of functions. Reasonable for a trusted API, worth remembering if the model is ever swapped for an untrusted source.

Glossary

TermMeaning here
Chunk / DocumentOne indexed passage — a Marker block or a Markdown section. Haystack's Document = {id, content, meta, embedding, score}.
Embedding / vector384 numbers representing a text's meaning. Similar meaning → nearby vectors.
Dense retrievalSearch by vector proximity. Catches synonyms and paraphrase.
Sparse retrieval / BM25Keyword search weighted by term rarity. Catches exact symbols and names.
Hybrid retrievalRunning both and merging. This repo's core choice.
Bi-encoderEncodes query and passage separately, so passages can be precomputed. Fast, less precise.
Cross-encoderReads query and passage together and scores the pair. Precise, too slow for a whole corpus — used only on finalists.
RerankingRe-sorting a shortlist with a better, slower model.
RRFReciprocal Rank Fusion — merge ranked lists using ranks, not scores.
top_kHow many results a stage returns. dense_k, sparse_k, final_k.
Vector databaseStore built for nearest-neighbour vector search. Here: Qdrant, embedded on disk.
Ingestion / indexingThe one-time build of the searchable indexes.
IdempotentRe-running changes nothing. Achieved via content-hash IDs + SKIP.
Context / groundingThe retrieved text pasted into the prompt. The whole point of RAG.
HaystackThe orchestration library supplying Document, stores, retrievers, embedders, rankers.
